# 試し書きから見た推奨 (ADR-0027)

## 書いたファイル

- `c1-missing-ndl-version.yaml`
- `c2-ndl-1-1-with-mtu-read-by-1-0.yaml`
- `c3-ndl-1-0-with-mtu-user-error.yaml`
- `c4-future-check-same-subnet-different-vrf.yaml`
- `c5-sugar-string-and-meta-extra.yaml`
- `c6a-before-rename.yaml`
- `c6b-after-rename.yaml`

## 推奨 (約 950 字)

6 つの場面を書き分けたうえで、約束の案は**「(a) 前方互換は error のまま」を基線にし、
版の不整合だけ (b) の案内を重ねる**のがいちばん使い勝手がよい。(c) 「未知のキーを warning に」は
採らない。

理由 1 (C1): `ndl_version` は「既定値 1.0」ではなく**必須フィールド**にしたい。既定値があると、
1.0 の mlndl ではたまたま通るが、2.0 の mlndl で既定が変わった瞬間に意味が黙って変わる。利用者は
「書き忘れた」のか「わざと省いた」のかを区別できない。一行足す負担は小さく、文書とも整合する。

理由 2 (C2・C3): 版の違い (1.1 の YAML を 1.0 の mlndl で読む) は、pydantic の「未知キーだ」の
error では利用者の視点と原因が噛み合わない。読み込みの最初に `ndl_version` のマイナー番号を
パッケージが宣言するマイナー番号と比べ、**宣言より新しければ 1 本の error で止める** ((b) の案内)
のが親切。書き手の誤り (C3) と区別できる。(c) で `mtu` を黙って捨てると、「1.1 の意味」(検査の追加
など) が 1.0 で見過ごされる副作用が大きく、採らない。

理由 3 (C4): 版の約束と別に、**`validate()` の結果の約束**が要る。1.x の間に足せるのは warning 以下
だけ、error に昇格するのはメジャー更新だけ、と明記すれば、1.0 で書いた YAML は 1.x の最後まで
「error なしで読める」ことが保証される。新しい検査は warning として入れ、`--strict` は CI 用に留める。

理由 4 (C5): 残す形を 2 つ約束に書く。`attaches_to` の**文字列の糖衣構文**と、`meta` **だけ**が
未知のキーを受け付けること。(c) を採らないことで、「`meta` だけが例外」の境界を保てる。

理由 5 (C6): 名前の直し (`lag` → `lags` など) は破壊的なので **2.0 でだけ**行う。1.x の間は読み替えず、
2.0 の mlndl で旧名を見たら ADR-0025 と同じ流儀で「移動先を示す error」。1.x で早く直したい誘惑には
乗らない方が、下流のツールの切り替えが進む。

まとめると、ADR-0027 の約束は次の 5 項目になる:

1. `ndl_version` は必須。主番号が合わなければ error。マイナーが新しければ「版が合わない」の 1 本の error。
2. 1.x の間に許すのは**加算のみ** (キー・値の追加、値域の拡大、検査の緩和、warning の追加)。
3. 検査の**error 昇格はメジャー更新**でだけ。`--strict` を既定にしない。
4. 残す形: `attaches_to` の文字列糖衣構文、`meta` の `extra="allow"` (ここ**だけ**)。
5. 名前の直し・形の変更は 2.0 で一括。1.x の間は読み替えない。

## 技術的疑問 (network-tech-reviewer へ)

- C4 で挙げた「同じ /N サブネットの L3 IF が別 VRF にある」は、EVPN VRF-lite や意図的な leaky では
  普通に起きる。warning で妥当か、それとも info か、network-tech-reviewer に意見をもらいたい。
- C2 の「マイナー版で加算できるキー」の例として `mtu` を使ったが、インターフェース MTU の意味
  (L2 の MTU / L3 payload MTU / PMTU) はベンダーで揺れる。単純な任意フィールドで足せるのか、それとも
  ADR 1 本かける重さの変更なのかは、1.1 の候補を増やす前に見極めたい。

## dsl-designer・linguist への引き継ぎ

- C6 で示したとおり、改名は 2.0 に積んで一括で済ませる案を推奨している。改名の時期をずらして複数の
  2.x を切る案はコストが大きいので採らない前提。
- 糖衣構文 (`attaches_to: esxi-01`) を「約束の一部」と書くときの用語 (糖衣構文 / 短縮形 / 文字列形式)
  は、リファレンスの既存の書き方にそろえたい。
